# ArchiveX v0.1.2-rc5 发布说明

## 主要变更

- 修复自动校验与发布流程中的后端测试配置：CI 在运行测试前创建仅含
  `WEB_AUTH_TOKEN=ci-test-token` 的测试专用 `.env`，避免测试收集阶段导入任务
  模块时，因缺少必填认证令牌而失败，使后续构建和发布检查能够继续执行。
  测试令牌仅用于 CI runner，不改变部署认证配置，也不覆盖本地 `.env`。
- 令牌通过配置文件提供，不导出为环境变量，保留 `Settings(_env_file=None)`
  对缺失必填配置的校验能力；同步补充自动发布文档中的配置说明。
- 相对 rc4，本次没有新增界面、归档、补档或全量扫描功能，也没有修改运行时
  源码、依赖和部署配置。已部署 rc4 的用户可按维护计划升级。

## 镜像

```text
ghcr.io/inp146/archivex:0.1.2-rc5
ghcr.io/inp146/archivex-web:0.1.2-rc5
```

CI 校验通过后自动构建并发布 linux/amd64、linux/arm64 镜像。

## 升级

从正常运行的 v0.1.2-rc4 升级，无需数据库迁移：SQLite schema 仍为 v3，
补档表及字段与 rc4 相同；无需运行 v2 → v3 离线迁移或重新搬移状态数据。
API、任务消息格式、媒体目录和环境变量要求均未变化，保留现有配置及密钥即可。
CI 测试令牌不得用于生产。若仍使用 rc2 或更早数据库，应先按 rc3、rc4 的
历史发布说明完成相应迁移，不能套用本节的 rc4 升级步骤。

本次没有迁移所需的长时间停机，但镜像替换会重启服务，建议安排短暂维护窗口：

1. 暂停手动任务提交，先停 scheduler，等待已投递及延迟重试任务完成，再停止
   API、crawl/media worker 和 Web，避免升级期间中断归档写入。
2. 停止所有写入后，建议备份业务 SQLite、twscrape 会话数据库、归档 JSON 和
   媒体，并保存本地 Compose 配置及密钥。可使用现有
   `docker compose run --rm tools backup`；确认备份的是 `state_data` 卷中的
   实际数据库，而非过期的主机副本。该工具不包含 Redis；若队列未排空，需
   额外保存与业务库一致的 Redis 持久状态。不要执行 `docker compose down -v`。
3. 将 API、crawl/media worker、scheduler、tools 及 state-migrate 的后端镜像
   统一更新为 rc5，Web 更新为 rc5，保留存储卷和挂载；由操作者拉取并启动。
   已完成的状态迁移无需重做，原有 state-migrate 检查仍可按 Compose 流程执行。
4. 启动后检查 `/ready`、登录、账号数量、任务历史及媒体读取，并验证普通同步
   和单条补档。自动发布流水线不会连接部署机器或替操作者启停服务。

回滚到 v0.1.2-rc4 时，先暂停投递、停止 scheduler 并等待活动任务完成，再停止
应用服务，将上述镜像统一切回 rc4 并启动。两版运行时代码、数据库和任务格式
一致，可沿用当前数据库、归档与 Redis 状态，无需降级迁移、清空队列或恢复
升级前备份。若另因数据损坏需要恢复备份，应停写并恢复匹配的数据库、会话库、
归档与队列状态；恢复旧快照会丢失其后新增内容。回滚到 rc3 或更早版本的限制
仍按历史发布说明执行。

从 GitHub Release 下载本版本 docker-compose.ghcr.yml。将镜像版本合并到本地
docker-compose.yml，保留认证令牌、端口和存储挂载等本地配置，再按上述升级步骤操作。
