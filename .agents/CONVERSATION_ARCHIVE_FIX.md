# 折叠帖子串漏归档修复

本文记录最初修复。后续缓存复用、单条失败持久恢复及视频解析修复见
[POST_RECOVERY_IMPLEMENTATION.md](POST_RECOVERY_IMPLEMENTATION.md)；
手动完整扫描入口见 [FULL_SCAN_UI.md](FULL_SCAN_UI.md)。

## 现场证据（2026-10-12）

目标账号：`uyu1289742`，稳定用户 ID：`1960693507158630410`。
示例回复：`2109013981524635821`。

生产 rc3 归档库中不存在示例回复，但使用同一生产抓取凭证调用
`TweetDetail` 能读取它。账号同步记录显示成功，首次抓取 173 条。

原始 `UserTweetsAndReplies` 响应的会话模块在
`metadata.conversationMetadata.allTweetIds` 中列出 18 条帖子 ID，包含示例回复。
模块只提供部分完整 Tweet 对象。旧适配器调用 twscrape 的已解析时间线，丢失会话
元数据，没有补查折叠内容；生产库中该串仅有 4 条，缺少 14 条。

因此，之前“X 时间线没有返回这条”的说法不准确：X 返回了这条的 ID，
程序没有读取 ID 并请求其完整内容。

## 修复行为

- `TwscrapePostSource` 改为逐页读取原始时间线，继续使用 twscrape 的 Tweet 解析器。
- 递归读取会话元数据中的有效 `allTweetIds`；只有未解析、未在本次同步处理过的
  ID 才补查 `TweetDetail`。跨模块、跨页去重。
- 在交出当前页可见帖子前完成补查，并先交出补出的内容，避免可见的已归档帖子
  触发连续 20 条停止条件而跳过折叠回复。
- 补查结果仍校验帖子 ID 和作者；其他作者不会变成该账号的顶层归档观察记录。
- 详情不可读取时抛出可重试错误，不把 `None` 当作已删除并静默报告同步成功。
  已失效的会话成员也会导致同步错误，需要后续诊断，不能据此承诺收齐所有内容。
- 详情查询的账号锁错误保留 `TweetDetail` 队列及解锁时间，复用现有任务重试。
- 上游异步生成器在提前结束、取消或失败时仍会关闭并释放请求上下文。

不新增环境变量、数据库 schema 或媒体下载路径。折叠串会增加详情请求数量，
详情按现有串行抓取方式执行。

## 验证

- `tests/test_source.py` 与 `tests/test_sync.py`：42 项通过。
- 使用修复代码在生产容器内执行一次性只读抓取验证：仅读取当前第一页，
  输出 21 条目标账号帖子；会话元数据中的 18 个 ID 全部有完整内容，
  示例回复已补出。没有写入归档库或启动、停止、重启应用服务。
- 全量后端测试：181 项通过，1 项失败。失败来自修复前已存在的未跟踪文件
  `tests/test_post_model_media.py` 中的视频空 URL 测试，与此次时间线修改无关；
  该文件及媒体解析代码保持原状。

## 生产生效与补档

生产容器当前仍运行原 rc3 镜像。操作者需要将包含本次代码的后端镜像更新到
部署配置中，手动执行受控部署。既有进程不会热加载此修改。

更新后，手动同步 `uyu1289742` 即可通过当前第一页中的会话元数据补齐此次
遗漏；帖子、观察关系和媒体继续经过现有幂等入库和媒体任务流程。

更早历史中、不在本轮增量分页范围内的折叠串仍需完整扫描。可使用现有
`ARCHIVE_INCREMENTAL_KNOWN_POST_LIMIT=-1` 在受控补档期间关闭增量提前停止，
完成后恢复原配置；本次没有更改任何本地或生产环境变量。仅凭本次修复和
一次增量同步，不能宣称全部历史数据已经补齐。
