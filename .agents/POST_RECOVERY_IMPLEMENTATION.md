# 视频解析及折叠回复持久补档

日期：2026-10-12。接续 `CONVERSATION_ARCHIVE_FIX.md` 和 `FULL_SCAN_UI.md`。

## 视频解析

工作区已有“过滤空视频地址”的修复。本次补齐空白地址、异常码率的处理：
先排除空或纯空白地址，再在有效版本中选择最高有效码率；缺失、非数字、布尔值、
负数、NaN、Infinity 不参与码率优先级比较。有效地址去除首尾空白。

旧归档 JSON 仍保留有效视频版本时，重新同步/全量扫描会通过当前解析器重新
建立缺少的媒体记录，再沿用媒体任务队列下载。已完成文件继续复用。没有对生产
数据执行扫描、补写或下载；旧 JSON 也没有有效地址时，需要重新读取 X 的内容。

## 复用完整快照

`ArchiveRepository.cached_post_snapshot()` 仅复用 availability=available、原始
JSON 存在且可解析、ID 匹配、作者一致的完整快照。占位、partial、unknown、
缺失文件、损坏 JSON 或编码错误都不会被当成完整内容。

`TwscrapePostSource` 逐页补查折叠回复前检查缓存，复用成功时不请求 TweetDetail。
可见时间线提供的新快照仍正常解析入库。没有新增定期删除/编辑复查调度器。

内容和观察关系分别处理：原先仅作为引用保存的完整内容，仍可新增当前账号的
观察关系，不需要重新请求正文。未建立观察关系的补出内容优先交给同步服务，
避免被连续已知帖子停止条件跳过。本次保留现有作者/行为主体筛选策略，未扩展为
归档会话中所有其他作者的独立回复。

## 单条失败独立恢复

新增 `archive_post_fetches` 辅助表，以归档账号 ID + 帖子 ID 为键保存发现来源、
状态、尝试次数、错误与时间。它不依赖 posts 外键，不为缺少作者的 ID 伪造帖子。
状态为 pending、completed、unavailable、ignored。

在详情请求前先记录本页全部缺失 ID；缓存完整但尚缺观察关系的内容也记录，
保证中途取消、进程退出或整体接口失败后仍可恢复。成功入库时，内容、观察关系
与对应补档完成状态在同一个事务中提交。清除任务历史不会删除待补清单。

单条请求失败、空响应或解析失败保持 pending，同页其他内容继续归档。
已经尝试过的待补 ID 不会在每轮时间线中重复查询，而由独立任务处理。
详情端点账号锁定时停止当前运行的后续详情请求，继续读取可用的时间线分页；
时间线整体无法读取或 GraphQL features 失效仍保留原有账号级错误与重试语义。

明确的 focal tweet 不存在响应或匹配其 ID 的 tombstone/unavailable 记录才进入
unavailable，不再自动重复查询；其他回复的 tombstone 不能影响 focal tweet。
这表示不可访问，不据此声称已删除。原因不明保持待补，已归档内容不删除。

同步结束仍有 pending 或重试耗尽的未解决记录时，sync run 和结果显示 partial，保留成功内容
的进度。同步任务负责分发 `archivex.fetch_post_detail` 单条补档任务，复用现有
crawl 队列、串行 worker、退避、账号解锁时间、任务超时及尝试上限。补档失败
不会要求重新跑整页；即使后续增量扫描未翻到旧位置，仍会分发遗留待补记录。
单条任务使用账号 + 帖子 ID 的独立锁，失败列表也以该组合区分，不把同账号
不同帖子的失败合并。

补档成功仍经过 `ingest_item()` 并投递媒体任务；内容已存好但后续媒体投递失败时，
重试可以复用快照继续投递。队列关闭的测试/开发模式使用同步恢复，不创建额外
后台进程；失败记录仍保留，下一次同步或手动重试可继续处理。

## 界面和接口

账号页显示待补/不可访问数量、ID、原因与尝试次数，并提供手动重试，包括重新
检查不可访问内容。待补减少时刷新归档列表及账号统计。任务中心显示“帖子补档”，
同步显示“部分完成”，不可访问和无需补档有独立展示；单条任务支持重跑和批量
重试失败。历史同步结果表示当时扫描结束的状态，当前剩余数量以账号页为准。

```text
GET  /api/accounts/{x_user_id}/post-fetches
POST /api/accounts/{x_user_id}/post-fetches/retry
```

## 后续：不可访问和重试耗尽退出待补

现场五条失败记录的真实 TweetDetail 响应为 HTTP 200、匹配 focal ID 的
TimelineTweet 空 tweet_results，以及 Top/Bottom 两端 TimelineTerminateTimeline。
该返回没有 tombstone 或错误 144，因此最初未识别不可访问。现已识别这种完整
结束的空占位；缺少终止标记、存在整体错误或只命中其他 ID 时仍不据此分类。
不可访问记录不再导致同步持续显示 partial，也不进入自动补档队列。

原因仍无法确定时，单条任务最终失败会设置 retry_exhausted，退出自动待补，
保留错误和尝试历史；手动重查/重跑可解除该标记。辅助表自动添加兼容列，
旧库已耗尽且没有活动补档任务的失败记录会一并标记，避免每次账号同步再建
一轮任务。实际状态仍为 pending，retry_exhausted 区分需要人工处理的失败，
不会把重试耗尽当成已删除。

账号页仅在有自动待补时默认展开；不可访问和重试已停止的记录收进默认折叠
的“补档历史”，保留手动重新检查入口。明细优先展示仍在自动补档的内容。
