# ArchiveX v0.1.2-rc6 发布说明

## 主要变更

- 新增按账号选择“归档内容”：原创帖（含引用帖）、回复、转发帖三个选项独立
  控制。添加账号时可在首次同步前选择范围，账号详情页修改后自动保存，并显示
  保存状态或错误。新账号和已有账号默认全部开启，保留原有归档行为；内容选择
  与定时归档总开关相互独立，修改范围不会启用或暂停账号。
- 普通同步、定时同步、手动全量扫描和独立单条补档均遵循账号设置。同步使用
  本次运行开始时的设置，运行中修改影响后续同步；单条补档在详情解析后读取
  当前设置。首次导入数量上限只计算所选类型，被排除的条目不计入连续已知帖子
  停止条件；三个选项全部关闭时跳过时间线扫描，但既有媒体失败重试仍可执行。
- 关闭类型后，不再通过该类顶层内容新增或更新归档；关闭转发帖也不会通过新
  转发保存其原帖及媒体。已有帖子、观察关系和文件保留，已开启的引用帖、回复
  或转发仍保存所需的原帖上下文，其他作者的上下文不会作为该账号的独立帖子。
  这是归档范围设置，不是删除历史数据或隐藏已有时间线内容的功能。
- 补档解析到被排除的类型时，将该 ID 标记为 `ignored`，退出待补统计和自动
  重试。重新开启任一类型会把该账号此前忽略的 ID 重新置为待补；因这些记录
  没有保存正文和类型，也可能重新检查其他作者的 ID，作者校验仍然有效。
  重新开启不会立即投递历史扫描；需要完整回补时手动执行“全量扫描”，仍受
  X 可返回历史范围、限流、超时和现有队列约束。
- 账号创建接口新增 `archive_originals`、`archive_replies`、`archive_reposts`
  三个布尔字段；账号解析、列表和详情返回相应设置。账号修改接口支持部分
  更新，未提交字段保持不变，显式 `null` 或非法布尔值返回 422。旧客户端只
  修改 `archive_enabled` 或重新添加账号时省略新字段的调用仍兼容，并保留
  已存的内容选择；认证和账号稳定 ID 校验沿用现有规则。

## 升级

从正常运行的 v0.1.2-rc5 升级，需要一次启动时自动执行的数据库增补，无需手动
运行离线迁移：API 初始化会在事务中为 `observed_accounts` 幂等添加上述三个
归档设置列，均为非空布尔约束、默认值 1。`PRAGMA user_version` 仍为 3；
已有账号的启停状态、帖子、任务历史和媒体目录保留，重复初始化不会覆盖所选
范围。不能仅凭版本号仍为 v3 判断数据库完全没有变化。若实际库仍为 v2 或旧的
未版本化库，须先按 rc3 历史发布说明完成离线迁移。

无需新增环境变量、修改认证令牌或更换存储挂载；任务名和消息参数没有变化。
新版 Web 需要新版 API 返回并保存归档设置，新版 worker 才会执行内容筛选，
因此应统一升级，避免新旧服务混用。现有 Compose 的 worker 不等待 API 健康，
而 worker 自身不会补齐这三个列，首次启动顺序须由操作者控制。

建议安排短暂维护窗口，停机覆盖备份、镜像替换和数据库初始化；无需执行重建
全库或搬移媒体的离线迁移。备份耗时取决于归档体积，不能承诺固定停机时长。

1. 暂停手动同步、全量扫描、补档和设置修改，先停止 scheduler，等待已投递及
   延迟重试任务处理完，确认没有活动任务后停止 API、crawl/media worker 和 Web。
   所有启停和部署操作由操作者执行，发布流水线不会替部署机器执行这些步骤。
2. 在停止所有写入后备份业务 SQLite、twscrape 会话数据库、归档 JSON 和媒体，
   保存本地 Compose 配置及密钥。可用现有
   `docker compose run --rm tools backup` 创建并校验完整备份；确认备份的是
   `state_data` 卷内实际数据库，而非可能过期的主机副本。备份工具不包含 Redis；
   若队列未排空，须另行保存与业务库一致的 Redis 持久状态，不能只备份任务历史。
   不要执行 `docker compose down -v`。
3. 将 API、crawl/media worker、scheduler、tools 和 state-migrate 的后端镜像
   统一更新为 rc6，Web 更新为 rc6，保留本地配置和存储卷。由操作者拉取镜像，
   先启动 API 并确认数据库初始化成功，再启动 worker、Web，最后恢复 scheduler
   和手动任务提交。已完成的 state-migrate 状态卷搬迁无需重做，沿用其检查即可；
   它不代替 API 的本次归档设置补列。
4. 启动后检查 `/ready`、登录、账号数量、启停状态、任务历史和媒体读取。确认
   原有账号三个选项默认开启，修改设置能够保存并在刷新后保留；用可控账号
   验证普通同步、全量扫描和单条补档遵循范围，关闭类型不删除已有内容。
   重新开启后的历史回补应按需手动投递并评估请求量与磁盘空间。

回滚到 v0.1.2-rc5 时，先暂停投递、停止 scheduler，等待活动任务及延迟重试完成，
再停止其余服务并保留当前数据快照，将上述镜像统一切回 rc5。新增列是 v3 的
向后兼容扩展，rc5 初始化不会删除它们，旧版按列名读写账号；任务格式也未变化。
仅回滚应用版本可沿用当前业务库、归档和 Redis 状态，无需删除列、降级迁移、
清空队列或强制恢复升级前备份。

但 rc5 不识别内容筛选，会恢复原有全部类型归档行为；即使新增列仍保存为关闭，
也不会限制 rc5 的同步或补档。如必须维持排除范围，应暂停相应账号的定时归档，
并避免对其手动同步、全量扫描和补档。rc6 已忽略的补档 ID 不会因换回 rc5 自动
重新排队；已重新置为待补的 ID 则可能被 rc5 按旧规则处理。回滚不能自动撤销
升级后的归档或补档状态变更。

若确需恢复升级前数据，须停写并恢复匹配的业务库、会话库、归档目录和队列状态，
避免旧快照收到升级后残留的 Redis 消息或延迟重试；恢复会丢失快照之后新增内容
和设置。恢复工具不能原地替换 Docker 的 `/data` 挂载点，须按既有状态恢复流程
先恢复到停机的主机暂存目录，再安装到实际状态卷。回滚到 rc3 或更早版本的限制
仍按历史发布说明执行，不能套用本节的 rc5 回滚兼容结论。

从 GitHub Release 下载本版本 docker-compose.ghcr.yml。将镜像版本合并到本地
docker-compose.yml，保留认证令牌、端口和存储挂载等本地配置，再按上述升级步骤操作。
