# ArchiveX v0.1.2-rc4 发布说明

## 主要变更

- 修复时间线中折叠回复漏归档：读取会话元数据列出的帖子 ID，补查缺少的
  详情并去重。复用已归档的完整快照，补建当前账号的观察关系；仍校验作者，
  不把其他作者的独立回复归入该账号，也不保证 X 接口提供全部历史内容。
- 增加持久化单条补档。发现的缺失 ID 在详情请求前入库，单条失败不再阻断
  同页其他内容；后续同步可投递独立“帖子补档”任务，沿用现有抓取队列的
  限流、退避、超时和重试上限。进程中断或清理任务历史不会删除待补清单。
  已入库内容继续保留，补档成功后沿用媒体下载流程。
- 账号页显示待补、不可访问和重试已停止的数量、错误及尝试次数，支持手动
  重新检查；补档历史默认折叠。仍有待补或重试耗尽记录时，同步显示“部分完成”；
  明确不可访问的内容退出自动补档，不再单独导致部分完成。不可访问及重试
  耗尽均不等同于已删除，不删除已有归档内容。
- 新增单账号“全量扫描”和“全部全量扫描”。全量模式仅对本次任务取消首次
  导入数量上限及连续已知帖子停止条件，复用已有内容和媒体，不改变普通或
  定时同步配置。全部扫描包含暂停定时归档的账号，但不改变其启停状态；
  提交前显示账号数、暂停账号数及请求量提示，已有同步任务不会重复提交。
  重跑及失败重试保留全量模式。扫描仍受 X 可返回的分页、限流与超时约束，
  没有历史分页断点恢复，可能长时间占用抓取队列。
- 修复视频版本选择：忽略空白 URL，去除地址首尾空白，在有效地址中优先
  选择最高有效码率，正确保留零码率排序并忽略异常码率。重新同步或全量
  扫描可从仍含有效视频地址的旧 JSON 重新建立缺失媒体记录并下载，已完成
  文件继续复用；升级本身不会自动修复全部历史媒体。
- 增加账号、帖子、搜索和任务间的关联入口。归档账号作者进入站内账号页，
  其他作者打开 X；回复、引用和转帖提供关联帖子入口。帖子详情页目前是
  占位页，仅显示 ID、关联入口和 X 链接，不展示完整正文、媒体或会话串。
  搜索可限定账号并匹配转帖原文；任务列表、统计和失败记录按账号精确筛选，
  URL 保留关键词、账号、状态及分页，返回时恢复分类和滚动位置。长账号 ID
  保持字符串，避免精度损失；导航“媒体库”改为全部账号的媒体视图。
- 抓取账号的 HTTP 代理在设置时必须明确写出端口，如 `http://host:8080`，
  不再接受省略端口的地址。
- 新增本地版本准备脚本和自动发布校验。版本 tag 通过版本一致性、测试、
  前端构建及 Compose 校验后才构建镜像，确认双架构 manifest 后创建 Release，
  附版本化 Compose 和校验和；RC 保持预发布且不更新 `latest`。发布流水线
  不会自动连接部署机器、迁移数据或重启服务。

## 镜像

```text
ghcr.io/inp146/archivex:0.1.2-rc4
ghcr.io/inp146/archivex-web:0.1.2-rc4
```

CI 校验通过后自动构建并发布 linux/amd64、linux/arm64 镜像。

## 升级

从已完成 rc3 迁移的 SQLite schema v3 升级，无需运行 v2 → v3 离线迁移工具。
新版初始化会幂等创建 `archive_post_fetches` 补档表及索引，并在缺少时添加
`retry_exhausted` 字段；已有补档表的耗尽失败记录在没有活动补档任务时会补标记。
`PRAGMA user_version` 仍为 3，既有帖子、转帖、观察关系和媒体模型不变。
若实际数据库仍为 v2 或旧的未版本化库，必须先按 rc3 发布说明完成离线迁移，
不能直接启动 rc4。

原有普通同步无请求体调用仍兼容，新增全量扫描参数、补档接口和账号任务筛选。
应用运行不要求新增环境变量；新增的 `RELEASE_AI_PROVIDER`、`RELEASE_AI_MODEL`、
`RELEASE_AI_TIMEOUT_SECONDS` 仅供本地发布说明生成使用，不需要加入容器运行配置。
检查抓取代理设置，后续保存代理须使用带显式端口的 HTTP 地址；此改动不会
自动批量重写会话数据库中已有的代理值。

建议安排一次受控停机升级，避免新版 API/任务投递端与旧版 worker 混用：

1. 暂停手动同步、全量扫描和补档提交，先停 scheduler，等待已投递和延迟重试
   任务处理完，确认没有活动任务后停止 API、crawl worker、media worker 和 Web。
   新版增加 `archivex.fetch_post_detail` 任务，并向全量同步任务传入 `full_scan`，
   rc3 worker 不具备对应处理能力。
2. 在停止所有写入后备份业务 SQLite、twscrape 会话数据库、归档 JSON 和媒体，
   保存本地部署配置及密钥。现有 tools 服务可用
   `docker compose run --rm tools backup` 生成并校验完整备份；确认实际业务库在
   `state_data` 卷中，而非仅备份可能过期的主机 `./data/archive.sqlite3`。
   若队列尚未排空，还须保存 Redis 持久数据及其与业务库一致的状态，备份工具
   不包含 Redis。不要执行 `docker compose down -v`。
3. 将 API、crawl/media worker、scheduler 和 tools 的后端镜像统一更新为 rc4，
   Web 同步更新为 rc4，保留原有卷、媒体挂载、认证和并发设置。由操作者执行
   拉取及启动；初始化自动完成上述数据库增补，无需复制或重排媒体目录。
4. 部署后检查 `/ready`、账号数、任务历史、转帖/引用及媒体读取，再验证普通同步、
   单条补档和账号范围任务筛选。按需手动全量扫描补查较早历史；先评估请求量、
   队列占用和下载空间，不把一次增量同步视为全部历史已补齐。

回滚前停止新版所有写入和任务投递。新增表、字段属于 v3 的增量扩展，rc3
初始化不会删除它们，但 rc3 不会处理补档状态，也不支持新版补档任务及全量
任务参数；仅把镜像标签改回 rc3 不能保证队列兼容。先保留当前数据快照，
再恢复升级前一致的业务库、会话库、归档目录及 rc3 部署配置；恢复后不得让
旧库收到升级后遗留的 Redis 消息或延迟重试，应恢复匹配的队列快照，或在
确认任务可舍弃后隔离/清理这些投递，再由 rc3 重新安排同步。完整恢复会
丢失升级后新增的归档和状态变更。恢复工具拒绝原地替换 Docker 命名卷挂载点
`/data`，应先恢复到停机的主机暂存目录，再按已有状态恢复流程安装。

从 GitHub Release 下载本版本 docker-compose.ghcr.yml。将镜像版本合并到本地
docker-compose.yml，保留认证令牌、端口和存储挂载等本地配置，再按上述升级步骤操作。

## 发布验证

- 本次在当前工作区运行完整后端测试：282 项通过，1 条 Starlette/httpx 弃用
  警告；本地 Python 依赖检查通过。测试涵盖折叠回复、补档持久状态和独立任务、
  旧 v3 库初始化、全量扫描、视频解析、账号任务筛选及发布脚本。
- 本次构建版和 GHCR 版 Compose（含 tools profile）配置校验通过；此时镜像
  版本仍为 rc3，不能代替准备 rc4 版本后的发布校验。
- 既有 `.agents/POST_RECOVERY_IMPLEMENTATION.md` 与 `.agents/SITE_INTERLINKS.md`
  记录前端 TypeScript 检查和 Vite 生产构建通过，本次未重新运行前端构建。
  站内互联的浏览器检查为未登录状态，真实账号和任务数据由接口测试覆盖，
  登录后的完整人工浏览尚未完成。
- 既有折叠回复文档记录使用生产凭证进行一次性只读抓取，成功补出示例回复；
  这不是 rc4 部署验收。补档文档中的五条不可访问记录更正仅作用于本地数据库，
  不是本版本自动执行的数据修复。本次未启停服务或操作生产数据、队列。
